## 1. 用户明确提出的新增范围

| 编号 | 用户要求 |
|---|---|
| U-01 | 有方便进行各类设置的网页后台，并可通过公网访问。 |
| U-02 | 方便配置 AI 团队，支持多个 AI 团队并行。 |
| U-03 | 方便修改团队架构及业务流程。 |
| U-04 | 能直接和任意一个已授权 agent 对话，提出新要求或修改。 |
| U-05 | 一个团队并行多个任务时，能分别查看每个任务状态。 |
| U-06 | 每个后台页面都有固定的 AI 窗口，可缩小和展开。 |
| U-07 | 此窗口后台可以使用真实 Codex，但网页不需要呈现 Codex CLI；用户可随时提出对团队、agent 和各类配置的修改，由它实际执行。 |
| U-08 | 可以基于原 dsh 后台改造，也可以新建原生网页后台；未锁定必须重写或必须沿用原页面。 |

“直接执行”是用户对平台管理操作的代理入口，不是给模型无条件管理员权限；“任何配置可管理”不等于所有操作免批准，也不授权显示秘密值或让 agent 自我批准。既有无需重复请示、具体授权、凭据和独立审核要求继续适用。

## 2. 建议的对象关系

公司是管理范围，项目是代码、业务目标、数据与交付边界，团队是可复用的组织单元，不能把团队和项目硬编码成同一对象。

| 对象 | 建议的边界 |
|---|---|
| 团队 | 有稳定 ID、名称、职责、负责人、成员配置、可服务项目、流程模板、预算和并发策略。首版支持至少两个团队并行活动。 |
| 岗位与成员 | 岗位是责任模板，成员有持续身份。成员可以兼任岗位；界面分别展示身份、岗位和所选 harness，不以 CLI 名称代替成员。 |
| 成员的团队分配 | 同一成员可以有多份明确分配；其项目访问与工具权限不因加入另一团队而自动扩大。团队复制默认不复制秘密值、私有记忆或有效批准。 |
| 工作流定义与版本 | 描述业务流程和验收条件；可有草稿、已发布版本。团队可有多份模板。 |
| 工作流运行 | 首版建议每次运行明确绑定一个项目和一个主责团队；其他团队以显式委派参与。固定流程、组织、规则、工具和执行配置版本。 |
| 任务与执行尝试 | 任务是目标和验收单元，一次实际启动是一个执行尝试。重试、交接、新会话与原生续接分别记录。 |
| 对话 | 区分管理助手对话、成员咨询对话和任务执行对话，关联真实发送人、对象、项目、任务及执行实例。 |
| 变更与授权 | 保存变更目标、前后版本、适用范围、发起人、批准依据、操作 ID、结果和可逆性。聊天正文不是唯一控制记录。 |

组织架构中的“汇报给谁”是协作关系，不自动成为数据读取权或审批权。团队层限制只能在公司、项目、岗位和任务已有授权中收紧，不可把不同项目的权限取并集。长期记忆仍由既有 GBrain 方案管理，不另建以团队文件夹假装读取隔离的记忆系统。

## 3. CONSOLE-REQ-01：公网可用但非匿名开放

后台默认中文，桌面浏览器完整可用；窄屏至少支持查状态、对话、审批和暂停，复杂画布可提供结构化替代视图。公网使用指通过域名与 HTTPS 访问经过认证的后台，不是把原生 CLI 或未鉴权管理接口直接暴露到互联网。

建议首版采用所有者创建与邀请制，不开放匿名注册；具有本地可恢复的首次管理员初始化路径。提供登录、退出、会话失效、设备会话撤销、邀请与权限撤销；公网管理账号使用多因素认证。身份实现可复用经过验证的认证组件，具体选型由设计确定。

全站页面、管理 API、实时事件连接、对话、预览与下载均须执行服务端鉴权和对象级授权。WebSocket/SSE 连接不是无限授权；权限撤销与会话失效后必须停止相应新读取和写入。反向代理、TLS、请求来源、CSRF、速率及消息大小限制须有测试。

Codex app-server、其他 CLI 控制端口、MCP 内部入口、数据库和执行节点管理端口不得因开放网页而直接公网暴露。网页浏览器只连接平台受控接口，不持有模型 API Key 或平台数据库凭据。

作品预览、模型 Markdown、上传文件和生成的 HTML 都是不可信内容；输出转义、受控下载、隔离预览与访问授权属于首版要求。可执行网页作品建议使用隔离来源和受限 iframe，不与管理员界面共享脚本权限或凭据。

公网启用前必须完成登录、越权、撤权、跨站请求、危险内容预览和未鉴权接口负向验收。单独配置 TLS 或把监听地址改成 `0.0.0.0` 不满足验收。

## 4. CONSOLE-REQ-02：团队中心与并行执行

团队中心支持创建、复制、编辑、归档团队，管理成员和岗位、指定负责人、绑定项目、分配已授权 harness 配置、工具与 skills、工作流模板、预算和并发上限。归档前展示正在运行的工作，不能删除仍被任务引用的身份或产物。

多个团队可同时有正在执行的任务；一个团队可同时管理多个工作流和任务。全公司、项目、团队、成员及执行节点的资源限制共同决定调度，不能每个团队各自使用全部全局额度。

原 REQ-021 中全局 4 个、单项目 2 个真实 agent 的初始值不因本需求而自动增加。队列可以保存多于并发限额的任务，界面须区分排队和实际运行。管理助手的真实调用也纳入额度与费用；用户点击暂停等确定性控制不得先等待一个模型运行名额。

建议为管理交互设置可配置的调度优先级或预留配额，在不增加总额度、不强杀已接受工作的前提下保持可用。具体默认值需通过参考环境测试确定；多团队并行不等于承诺无限进程、无限预算或每页启动一个常驻 agent。

并行代码任务使用独立工作副本、分支和任务目录；同项目的多团队修改需要显式整合和冲突处理。同一成员的并发执行拥有独立运行上下文，不能共用一份可写工作目录或原生会话制造并发。

## 5. CONSOLE-REQ-03：可编辑的团队组织架构

提供组织图和成员列表两种视图，支持增加、移除、替换岗位分配，修改职责、协作及审核关系，选择兼任或独立成员，配置模型路由、能力和资源限制。组织图、表单和自然语言编辑同一份版本化组织定义。

发布组织修改前检查引用、空缺岗位、审核独立性、权限和必要能力。不能仅拖动连线就扩大权限，也不能把开发者自己变成独立审核者。结构变更显示受影响的模板、未开始步骤和活跃实例。

普通组织变更默认影响新运行；对已有运行需要明确选择适用对象与交接点。更严格的禁止和撤权按原 REQ-011 对新操作生效，权限扩大不自动追加到正在运行的实例。移除忙碌成员应支持排空后退出或受控交接，而非直接丢失任务。

## 6. CONSOLE-REQ-04：可视化业务流程与版本管理

提供自然语言编辑、流程画布和结构化表单，三种入口修改同一份定义。支持顺序、并行、条件、聚合、人工输入、批准、独立审核、返工、等待事件和有上限的循环；循环不通过偷偷放宽普通依赖图校验实现。

节点明确目标、岗位、输入、产物、依赖、执行配置、工具、验收、预算、超时和失败处理。发布前检测缺失引用、不可执行分支、无退出条件循环、审批或审核缺失、不可用工具和无效执行节点。

模板复制、版本比较、发布和历史查看可用。运行实例保存引用的完整版本；修改模板不直接修改历史或活跃运行。针对运行中流程提出改变时，先显示哪些已完成结果不变、哪些未开始步骤受影响、是否需要暂停、交接或重新审核。

业务流程变化导致验收目标或产物改变时，原来的批准和审核按版本关系失效，不能用“只是从聊天改了一句话”绕过质量要求。

## 7. CONSOLE-REQ-05：与任意已授权成员直接对话

从团队组织图、成员卡片或任务页进入成员对话，不能只能与总协调者聊天。界面始终显示接收成员、所属项目／团队、任务和当前执行实例；同一成员执行多个任务时，用户必须能够明确选择目标。

建议提供三个清楚的交互入口：咨询讨论、追加任务要求、创建新任务。咨询不自动扩大任务范围；新要求保存为可跟踪的任务变更；另起任务有自己的产物和验收。

对运行中的成员发消息，需要显示已持久化、已投递、何时采纳或不能采纳。常规追加要求在下一可用步骤边界处理；有原生可靠 steer 能力时可按其真实语义使用。立即停止使用独立的确定性控制入口，不依赖聊天被模型及时读到。

成员空闲时可启动有身份和授权的新咨询实例。原生不支持续接的产品仍可通过版本化产物与获准上下文继续工作，界面标为新实例交接；不得冒充原生会话恢复。读取历史对话成功不等于能继续同一个原生进程。

同名 agent、团队复制或成员并发不能误投递。跨项目聊天不自动导入其他项目会话和私有记忆。所有者提出业务变更后，相关协调者、执行者和审核责任通过任务记录同步，不能只留在私聊里造成团队信息不一致。

## 8. CONSOLE-REQ-06：全站固定的 Codex 管理助手

在已登录后台的应用外壳中挂载一个统一助手入口，覆盖概览、团队、成员、流程、任务、产物和设置页面。支持最小化、侧边展开和大窗口；可选择当前页面上下文或固定目标。页面路由切换不销毁已接受工作和对话记录；刷新后可恢复。

建议桌面端采用右侧可调宽的抽屉和最小化入口，窄屏采用全屏覆盖。最小化不能遮挡关键按钮，展开不强迫用户离开当前工作页面；键盘焦点、关闭返回焦点、屏幕阅读语义和错误状态遵循主规格的无障碍目标。

后台默认通过真实 Codex harness 运行，使用已批准的 Codex 模型配置和固定 credentialRef；本需求没有批准替换模型、提供商或思考等级。网页用自己的聊天、变更卡片、操作进度和审批 UI，不需要显示终端或嵌入 CLI 界面。

全局助手与开发者 Codex、规划者 Codex 和审核者保持不同的身份、会话、权限和资源记录。不会每打开一页就创建独立常驻 Codex，也不会把所有登录用户共享在一个上下文中。会话按人类用户和有效作用域隔离。

发送时固定页面所代表的对象 ID、所选团队／项目／任务及版本，明确展示作用范围。用户发送请求后再切换页面，不得把已发请求重定向到新页面的对象。页面数据仅以白名单、脱敏且经过服务端授权的结构提供，不能直接把整个 DOM、隐藏字段、秘密表单或无关项目数据交给模型。

助手需展示真实输出、已调用管理操作、结果、待批准项和失败原因。后台不能提供完整原生轨迹时标记观测边界，不编造思考过程、工具调用或成功结果。Codex 不可用时常规表单、状态、批准及停止功能仍可用，不静默换一个模型冒充。

## 9. CONSOLE-REQ-07：自然语言能够真正修改，而非只给建议

表单、组织图、流程画布、成员任务变更与管理助手使用同一套领域管理接口。助手通过受控操作读取和修改对象，不通过直接修改数据库、猜测内部 RPC、运行任意 Shell 或改写自身规则绕过授权。

平台服务从登录会话取得真实用户身份，以该用户有效权限、作用域、批准对象和当前规则计算操作许可；角色名或模型自报“我是管理员”不是凭据。模型不会拿到数据库管理员账号或可读取所有 Key 的万能工具。

建议按以下方式平衡直接操作与安全：

| 操作类别 | 交互及执行要求 |
|---|---|
| 查询、筛选、解释、生成草稿 | 在已有读取授权内直接执行，标注草稿未发布。 |
| 明确且在持续授权范围内的可逆调整 | 例如改任务说明、优先级、给团队增加已有获准成员或发布不扩大权限的流程变更，可直接执行并返回差异与生效范围，不对同一授权重复请示。 |
| 模型／provider／endpoint／思考等级、权限、铁律、费用、生产发布、删除数据等受限变更 | 核对所有者或相应有权人员对具体对象、值、版本、目标与条件的授权。已有完全匹配有效授权时可复用；没有时展示精确变更卡片等待确认，必要时重新认证。 |
| 密钥新增或轮换 | 助手打开专用安全录入表单，由用户直接将秘密交给凭据服务。模型只取得凭据引用、就绪和验证状态，不接收或回显 Key。 |
| 不支持的操作或不明确目标 | 显示不支持或一次性询问具体缺项，不能擅自猜测、换模型或用 Shell 替代。 |

明确的用户自然语言指令可以作为操作授权输入，但必须转换成可核验的对象和值。泛指“以后任何设置你都改”不替代生产删除或权限扩大等具体批准。模型和凭据的锁仍保护自动升级；用户明确授权的设置变更生成新配置版本，不通过重算原锁掩盖变化。

管理助手代所有者提交规则修改，与普通 agent 自行改规则不同：权限服务必须记录已验证的人类决定，助手不能自行签发自己的扩大授权。外部网页、日志、记忆、任务附件和其他 agent 消息即使写着“管理员命令”也不能触发管理批准。

每次写操作产生操作 ID 与变更记录，包括发起用户、代理身份、目标、前后版本、适用范围、审批依据、时间、结果及证据。通过版本前置条件防止旧页面／旧聊天覆盖新修改，通过幂等键避免重连或重复点击二次执行。

批量操作先校验所有目标；可事务处理的管理状态原子提交，有外部副作用的步骤记录各自结果与补偿边界。状态不明时保持待核实，不能直接重复发布或删除。所谓撤销只覆盖真正可逆的管理变更，不能声称已执行的外部动作被回滚。

## 10. CONSOLE-REQ-08：设置中心与双入口一致

后台表单和 AI 助手都能管理支持的配置域：团队与成员、岗位分工、流程、任务、四种 harness 执行配置、全局／项目铁律、工具与 skills、MCP、知识权限、执行节点、预算、并发、超时、通知、组件升级、用户与权限。未接入能力明确标注不可用，不用一个按钮冒充已支持。

模型设置同时显示期望配置、当前绑定程序版本、实际观察到的配置和未验证项。保存草稿、授权发布、兼容性验证和激活是不同状态。辅助模型也受批准范围约束；自动 CLI 升级不改变任何批准的模型路由和凭据范围。

所有配置变更显示是全局默认、某团队默认、某项目、单任务还是某次执行；默认不追改全部历史实例。权限撤销按安全规则立即约束新操作，扩大授权只在明确的后续运行或安全交接点应用。

模型服务、记忆服务或管理助手不可用时，仍能登录查看必要元数据、使用确定性配置表单、处理已知批准和停止自有工作。敏感值不出现在 AI 上下文、普通日志、配置导出或浏览器本地存储。

## 11. CONSOLE-REQ-09：任务可见性与页面组织

全公司概览、团队看板、项目看板、工作流运行图、成员任务列表和单任务详情是同一组持久状态的不同视图，不分别维护“看起来完成”的状态。状态沿用主规格，另外可展示取消已请求／已确认及连接状态，不将失联当作成功。

任务详情至少显示：主责团队、项目、工作流及版本、执行成员与岗位、实际 harness、模型配置、当前步骤、排队或等待原因、最新活动时间、耗时、可观测用量、依赖、产物版本、测试与审核、待决定事项、失败及下一责任人。

进度能量化时显示完成的步骤／检查项及分母；不能量化时显示阶段和未知，不生成虚构百分比、预计结束时间或完成声明。可按团队、项目、成员、状态、优先级与时间筛选，提供失败与等待项入口。

建议页面结构：公司概览、团队中心、项目中心、工作流、任务与运行、成员与对话、产物与知识、审批与审计、设置中心。组织图与流程图是不同页面／视图；审批、权限和执行版本不能仅藏在聊天里。

每个页面同时保留全局助手入口；成员对话与助手管理对话的发送框清楚标识目标，避免把给工程师的业务指令送给管理员助手，或反过来。

## 12. CONSOLE-REQ-10：断线、重启和并发修改

浏览器关闭、刷新、换页或网络断开不终止服务端已接受任务。控制事实先持久化再确认接收。重新连接时从可核验事件游标补齐，处理重复和乱序消息，不让旧事件覆盖新状态。

运行恢复、任务取消和外部副作用语义沿用 REQ-018，PostgreSQL 是控制事实来源，GBrain 不是运行队列。数据库不可用时不能确认新写操作成功；记忆不可用时只阻塞依赖记忆的步骤。

人工编辑和 AI 修改同时发生时，服务端校验目标版本；冲突时返回差异，由有效决定更新，不静默最后写入覆盖。撤权、成员归档、版本停用和会话失效的竞态都需要负向测试。

性能参考沿用 REQ-022 的数据集与平台 p95 指标；新增助手的“请求已接受”延迟与模型生成延迟分开统计。不能以平台页面更新速度承诺模型回复速度或多团队的实际交付完成时间。

## 13. 复用方案建议与已核实边界

建议采用“复用 dsh 底座，新增团队管理页面和全局助手”的方式，先做使用真实接口的端到端页面，再依据实测决定是否替换整套外壳。不要求照搬原聊天首页，也不先重写会话、工具、权限、进程和持久化基础。

| 已读仓库材料 | 可以借鉴／复用 | 不能直接认定已满足 |
|---|---|---|
| [client 分组](../../packages/client/README.md) | React 渲染、插件与 slot、会话、设置、审批和产物呈现。 | 公司级团队域模型、跨项目权限和统一管理助手。 |
| [ui-layout](../../packages/client/ui-layout/README.md) | 应用外壳、可调面板与 `shell.overlay` 等扩展点。 | 当前布局状态为瞬态，尚非全站独立持久助手的合同。 |
| [ui-subagent](../../packages/client/ui-subagent/README.md) | 子会话目录、可续接成员的消息路径与状态。 | 一次性子任务目前是只读记录，不能证明任意成员都可持续对话。 |
| [Codex provider](../../packages/subagent/subagent-codex/README.md) | 真实 package-local 产品、app-server 协议和进程生命周期。 | 当前提供方的一次性最终文本结果，不能直接承担全局交互式管理助手的全部能力。 |

| [架构](../../docs/architecture.md) | Cordis 插件边界和受支持的 dsh profile 启动方式。 | 不授权另起绕过产品入口的正式服务或重复维护两套权威状态。 |

上述为固定提交中的文档与有限源码阅读，不是安装、渲染、性能或安全复验。本地 agent 的当前 Windows 验证结果尚未收到。

建议数据流为：网页表单／流程图／AI 助手 → 统一管理接口与权限判定 → PostgreSQL 控制状态／操作记录 → 调度与执行节点 → 真实 harness 和受控工具。管理助手的模型只提出或执行被授权的领域操作，不成为控制状态的权威。

真实 Codex 可以作为自定义 UI 的后台，而不用嵌入终端。OpenAI 的 [App Server 说明](https://openai.com/index/unlocking-the-codex-harness/)给出了双向 JSON-RPC、事件与审批交互；具体版本、协议、中转兼容性和可观察能力仍须按项目固定配置验证。

公网长连接和代理操作设计参考 [OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html) 与 [LLM Prompt Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)。这些资料支持威胁与防护方向，不证明本项目已实现防护，也不自动授权调用其他模型做安全检查。

## 15. 开发衔接与非目标

本补充不要求本地 agent 立即停止当前 P0-B 验证，也不因为新增网页范围就重新跑已经通过且未受影响的旧检查。先完成当前本地验证与问题交接；指定规划者随后评估新增范围对数据模型、适配器能力、身份、批准和版本固定的影响。

阶段层面建议：P1 的控制域基础包含团队与人类身份、管理操作和版本合同；P2 的最小真实闭环带任务状态页、一次成员消息与助手受控变更；P3 完善组织／流程可视化、全站助手和集中设置；公网启用须先通过专项安全准入，恢复与升级仍按 P5 实测。这里仅指出产品依赖，不提前编写后续节点的逐文件实施计划。

不要等到 UI 最后阶段才定义 Team、Conversation、ChangeSet 与授权边界，但也不要让 P0-B 必须实现整个公网后台才允许结项。新要求不能放宽原四产品真实性、隔离、GBrain/PostgreSQL、三端交付或独立审核条件。

本次未决定视觉品牌、域名、认证服务提供商、服务器采购或新增收费服务；不需要用户现在提供这些才能完成当前无密钥验证。设计阶段可先给出原型与明确推荐，临近部署再收集真正需要的授权与材料。
