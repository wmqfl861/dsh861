Expected identity established from Ubuntu's signed archive metadata before download:

- Signed `InRelease` fetched from `https://archive.ubuntu.com/ubuntu/dists/{noble,noble-updates,noble-security}/InRelease` (HTTP 200 each; hashes in `logs-r48/`). Signature verification: `gpgv` with key `F6ECB3762474EDA9D21B7022871920D1991BC93C` ("Ubuntu Archive Automatic Signing Key (2018)") fetched from `keyserver.ubuntu.com` into the transient keyring `C:\dsh-r48-tqt3s7\gnupg-tmp` — **good signature** for both `noble-updates` and `noble-security` (exit 0; transcript in `logs-r48/`). Provenance note: the key did not pre-exist on this host, so it was fetched from Ubuntu's own keyserver into a run-local keyring; nothing was written to any global trust store. The signed-metadata-over-HTTPS chain stands on its own even without this gpgv step.
- `InRelease` bodies list SHA-256 for the `main/binary-amd64/Packages.gz` indexes; both match the actually downloaded Packages.gz bytes (noble-updates `da2bc015c88567e3215fa38c172f9a10b47d09d42c015bc4fa9f16776e5b1c39`, noble-security `e06fc640457672f6178289f29b7a3e63e77842bd09bbe9a29f51df63e25753b4`).
- Both signed Packages indexes (noble-updates and noble-security) carry the identical stanza: `Package: libcap-dev`, `Version: 1:2.66-5ubuntu2.4`, `Architecture: amd64`, `Filename: pool/main/libc/libcap2/libcap-dev_2.66-5ubuntu2.4_amd64.deb`, `Size: 595634`, `SHA256: 07f2462867569a2119a2ad0f1593232663f2d1612b791c230d22a8d73a15abee`. The base noble pocket still lists `1:2.66-5ubuntu2.4`'s predecessor `1:2.66-5ubuntu2`; the update pocket is the pin, cross-confirmed by the security pocket.
- Downloaded from BOTH `https://archive.ubuntu.com/ubuntu/pool/main/libc/libcap2/libcap-dev_2.66-5ubuntu2.4_amd64.deb` (rolling archive) and `https://snapshot.ubuntu.com/ubuntu/20260919T000000Z/pool/main/libc/libcap2/libcap-dev_2.66-5ubuntu2.4_amd64.deb` (official snapshot, pinned UTC timestamp; the script pins this durable form because the rolling pool drops superseded -updates versions — the exact failure r47 hit on bubblewrap). Both returned HTTP 200, 595634 bytes, SHA-256 `07f2462867569a2119a2ad0f1593232663f2d1612b791c230d22a8d73a15abee` — byte-identical to each other and to the signed-index digest.
- Package contents audited as data (`ar` container: `debian-binary` 2.0, `control.tar.zst` 1466 B, `data.tar.zst` 593976 B; Windows bsdtar 3.8.4 for the zstd members — the runner path uses `dpkg-deb --fsys-tarfile`, so zstd handling is a local-audit concern only):
  - Control: `Package: libcap-dev`, `Version: 1:2.66-5ubuntu2.4`, `Architecture: amd64`, `Depends: libcap2 (= 1:2.66-5ubuntu2.4), libc6 (>= 2.34)` — matches the signed stanza.
  - 102 data members, all relative (`./`-prefixed), no absolute paths, no `..`, no device members. Symlinks: `libcap.so -> libcap.so.2` and `libpsx.so -> libpsx.so.2` dangle inside the private tree (the runtime package is deliberately not taken); `changelog.Debian.gz -> ../libcap2/changelog.Debian.gz` and all man-page links resolve within the extraction root.
  - Required payload present as regular files: `usr/include/sys/capability.h` (8681 B), `usr/lib/x86_64-linux-gnu/libcap.a` (56650 B), `usr/lib/x86_64-linux-gnu/pkgconfig/libcap.pc` (211 B), plus `libpsx.a` (18412 B) and `libpsx.pc`.
  - `libcap.a` is a real `ar` archive of six ELF relocatable objects: `cap_alloc.o`, `cap_proc.o`, `cap_extint.o`, `cap_flag.o`, `cap_text.o`, `cap_file.o`. Deep ABI compatibility (symbol-level) is proven by the actual link on the Linux runner, listed as NOT_RUN locally.
  - Package test programs under `usr/lib/x86_64-linux-gnu/libcap2/tests/` (including binaries named `exploit`/`noexploit`) are inert data here: nothing from the package is ever executed, and maintainer scripts never run (`dpkg-deb --extract` only).
  - **Upstream quirk discovered:** the shipped `libcap.pc` declares `libdir=/usr/lib64` while the payload installs under `usr/lib/x86_64-linux-gnu`. A sysroot build consuming that file would search a nonexistent directory and fall back to host lookup paths. The script therefore generates a private `libcap.pc` with the audited absolute paths and restricts `PKG_CONFIG_LIBDIR` to it; the private pkg-config resolution (version + libdir) is asserted before Meson runs.
