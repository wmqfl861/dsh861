## A. Cordis unload and error-stack mechanics (read-only vendor facts)

1. `vendor/cordis/src/fiber.ts:691-712` — `Fiber._unload()` runs `await Promise.all(this._disposables.clear().map(async (dispose) => { await Promise.resolve(); await runDisposable(dispose) ... }))`. Effects registered directly on one fiber are disposed CONCURRENTLY (Promise.all), each after one microtask. Disposer errors are caught and reported via `ctx.logger.error`; `fiber.dispose()` still resolves.
2. `vendor/cordis/src/fiber.ts:428-443` — inside ONE effect, the disposers it collected run sequentially in reverse collection order (`.then` chaining in the effect's internal `dispose()`). So sequencing holds within a single effect's yielded disposers, but NOT between sibling effects on the same fiber, and not between fibers.
3. `vendor/cordis/src/fiber.ts:266-298` — `ctx.plugin()` registers the child fiber's unload as an effect on the PARENT fiber. A parent fiber's `_unload` therefore runs a child plugin's unload concurrently with the parent's other disposables.
4. `vendor/cordis/src/utils.ts:275-294` — `composeError(callback, getOuterStack)`: for async results, `handleError` splices `getOuterStack()` frames into the rejected error's stack. `getOuterStack` was captured when the effect/fiber was REGISTERED (fiber.ts:221-229, 456; `buildOuterStack` at utils.ts:291-294).
   - Attribution consequence: frames such as `Fiber._reload` / `Fiber._execute` / `Fiber.execute` / `new SubagentRuntime (index.ts:201)` / `RegistryService.plugin (test-invariants.ts)` that appear BELOW an async error's own frames are the registration-time outer stack, spliced at throw time. They are NOT evidence that a reload or plugin load was executing at dispose time. Both reproduced failures show exactly this spliced shape (`01-first-failure.normalized.log`; r43 `10-exposed-defects-diagnosis.md` described the same stacks).
5. `vendor/cordis/src/utils.ts:117-129, 170-225` — `createTraceable`: when a service is read through a context (`ctx.someService`), the service proxy's `ctx` property resolves to the USE-SITE context (`tracker.property === 'ctx'`). `vendor/cordis/src/registry.ts:199-204` sets that tracker on `RegistryService.ctx`.
6. `packages/session/session-projection/src/index.ts:273-292` — `SessionProjectionRegistry.register()` registers its ref-counted registration via `this.ctx.effect(...)`. Combined with fact 5, the registration effect rides the fiber of the context through which the registry was ACCESSED, not the registry's defining fiber. The class JSDoc (index.ts:188-198) states the same contract: "Registration is an effect (disposer rides the calling fiber)".
7. `packages/session/session-projection/src/index.ts:169-174, 284-290` — registrations for one key are ref-counted; the key disappears from `stateOf`/drives when the LAST registrant's effect is disposed. `stateOf` (index.ts:319-327) returns `undefined` for an unregistered key.

## B. Team teardown path (Defect 2 from r43)

1. `packages/experimental/agent-team/src/index.ts:116-125` — inside the TeamService plugin's own `ctx.effect(... 'agentTeams.runtimeLifecycle()')`, the effect body calls `ctx.root.sessionProjections.register(teamProjectionDefinition)` and returns an async disposer that runs `try { await this.disposeRuntime() } finally { disposeProjection() }`.
2. ## C. Continuable-activation teardown path (Defect 1 from r43)

The continuation manager (and its `ContinuableActivationRegistry`) live in the inject child fiber; its creation stack (shown in the reproduced error) is the fiber's registration-time outer stack.
2. `packages/subagent/subagent/src/continuation-activation.ts:184-199` — the registry constructor registers, in order on the SAME childCtx fiber: (a) the `ctx.plugin(function activationOwner() {})` scope whose fiber structurally owns every Activation `AgentHandle` (`ownerCtx`), (b) a generator effect `yield scope.dispose; yield () => this.drain()` labelled `subagents.continuations()`. 3.
