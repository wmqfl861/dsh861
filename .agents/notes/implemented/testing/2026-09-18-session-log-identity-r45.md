# Agent Note: Header-identity log selection in the headless subagent expected suites

Status: implemented

English | [中文](2026-09-18-session-log-identity-r45.zh.md)

## Problem

The assembled-app subagent suites selected persisted Session logs by accident of enumeration. `subagent-diagnostic.expected.e2e.ts` picked "the parent log" with a full-text containment find over `'"subagent-diagnostic-parent"'`, and `subagent-inheritance.expected.e2e.ts` did the same for its parent while accepting any log whose first record merely had a string `parentSession` as the child. A delegated child's header carries the parent id inside its own `parentSession` field, and an unrelated Session can reference the parent id in event bodies, so whichever log `readdir` listed first became "the parent". The consumers CI run of the r44-B commit (run 35359781644) failed both suites exactly there: the diagnostic's "parent" was the child's log, and inheritance compared one child log against both goldens. Directory enumeration order is not a contract anywhere, so the suites were asserting against an arbitrary file.

## Decision

A test-only module, `apps/cli/tests/profiles/headless/tests/session-log-identity.ts`, selects logs by the durable identity of the first JSONL record. `sessionLogIdentity` validates one log's first record — valid JSON object, `type: 'session'`, string `id` — and rejects a malformed record by its source name instead of skipping it, because a skipped log could silently hide the parent or a duplicate. `selectSessionLogById` requires exactly one log asserting the target id: zero matches (a Session referenced only inside child headers or event bodies) and duplicate matches (two logs claiming one Session id) both fail with the sources listed. `selectDirectSubagentChild` requires exactly one candidate asserting the exact `parentSession`, an `id` of its own that is not the parent's, and `origin: 'subagent'`; a pinned `childId` (the diagnostic fixture's seeded child) must be asserted too. Selection returns the original entry bytes and its header untouched — it never rewrites or re-identifies a log. Both suites' `inspect` blocks call these selectors and consume the returned content, inheritance additionally asserting the child's file and id differ from the parent's, and the diagnostic verifying the seeded child's correspondence through the pinned id. A deterministic spec, `session-log-identity.spec.ts`, covers all 24 enumeration orders of a parent, its child, a reference-only Session, and another parent's child, plus reference-only rejection, duplicate and missing parents, malformed first records (invalid JSON, non-session type, missing id), sibling and grandchild and origin-less decoys, duplicate direct children, header field-order and CRLF tolerance with original-byte return, and input immutability. Two negative controls mutate only the helper — restoring the old full-text first-find parent selection fails six spec tests including the child-first order and the reference-only case; restoring any-`parentSession`-string child selection fails eight including the other-parent's-child-first case — and each mutant is restored byte-identically (SHA-256 re-verified) with the spec returning to 15/15.

## Alternatives considered

**Reusing the JSONL persistence's header codec.** The production `parseHeaderRecord`/`isHeaderLine` are not exported, and `scanLog` re-validates every event row, so header selection would start failing on event bodies it has no stake in; a first-record identity read is the whole need.

**Selecting by directory or file name.** Filenames are `encodeSegment` path-escaped Session ids, an encoding detail of one persistence backend; selection should rest on the record the format defines as identity, not on a name spelling that a backend may change.

**Hardening the existing `find` in place (for example, skipping logs whose header has a `parentSession`).** That keeps selection order-dependent — a duplicate parent, a reference-only log, or a second child still resolves to "whatever came first" — and the failure would move rather than disappear.

**Ordering the file list before selecting.** Sorting makes one lucky order deterministic but still selects by containment; any decoy that sorts first (or a duplicate the sort cannot distinguish) misleads exactly as before.

## Consequences

Every business assertion of both suites is preserved verbatim: the descriptor-less cold child, the `[diagnostic: corrupt]` containment, the parent golden, the final parent result and empty stderr; the physical `inherited.txt` absence, the read-only `source: 'delegation'` first child record, the two policy contexts with all positive and negative text checks, both goldens, the real write denial, and the final parent result. No golden was refreshed (`DSH_SNAPSHOT=refresh` never set) and no production package changed. The same text-match selection shape remains in `headless.expected.e2e.ts` and is deliberately untouched: this round's scope was the two failing suites, and a repository-wide replacement needs its own round. Two local Windows environment findings are preserved as first failures and not fixed here: under the canonical `pnpm exec vitest` wrapper the assembled app's profile node_modules install waits on a lock held by the wrapper's own pnpm process, so both suites time out at 30s with zero output, while invoking Vitest directly runs them to completion; and `normalizeSessionSnapshots` does not tokenize a Windows backslash cwd embedded in the workspace-write policy text, so the diagnostic suite's parent golden compare fails locally on `{{cwd}}` after selection succeeds — a spaceless ASCII TMP does not change it. CI (POSIX temp paths, no pnpm-exec parent) is the authority for both.
