# Agent Note: Owned fixture Contexts in the subagent-control and tool-team suites

Status: implemented

English | [中文](2026-09-16-owned-test-contexts-r42.zh.md)

## Problem

The `tool-subagent-control` and `tool-agent-team` specs built each fixture as a live Cordis runtime — `new Context()`, mounted `JsonlSessionPersistence`, an `AgentLoop` with a parent or lead agent holding the session's real kernel write lock — but `afterEach` only removed the temp directory. Nothing ever disposed the Context: agent write handles stayed open, their leases stayed held (a named Win32 semaphore or a POSIX `session.lock` FileHandle, per `SessionWriteLease`), and the control suite's `GatedAdapter` could pin a child's model call forever because its gate `await` ignored the request signal. A directory surviving or a small suite staying green proves nothing about release on Windows, where the semaphore never blocks removal and Node 26's DEP0137 makes GC collection of FileHandles an error rather than a cleanup strategy. The same suites also created fixtures whose teardown no one owned: a second `new Context()` in the control HMR case, and two full setups inside one team test.

## Decision

A test-only ownership ledger (`packages/subagent/tool-subagent-control/tests/owned-contexts.ts`, `OwnedTestContexts`) registers each fixture Context at the moment `new Context()` returns — before the first setup await that can fail — and its `mkdtemp` root the moment that directory exists. `afterEach` awaits `cleanup()`, which per fixture awaits `ctx.fiber.dispose()` to quiescence (the real AgentLoop and persistence teardown: cancel and await agents, close session write handles, release leases), runs an optional `afterDispose` observation, and only then deletes that fixture's root. A disposal or observation failure keeps that fixture's directory and its error while the remaining fixtures still clean; the collected failures rethrow as one `AggregateError`. `mountWriteOwnershipProbe` gives a test an independent backend over the same root so `open(id, 'write')` observes the real kernel write ownership: rejection with `SessionAlreadyOwnedError` while the fixture is live, takeover of the same directory — never a delete-and-recreate — after it settles. The control suite's `GatedAdapter` gate now ends when the request signal aborts (listener removed when the gate wins), so a test that fails before its manual release still tears down; normal held/parked/interrupt timing is unchanged because the gate only loses to an abort that did not fire during live assertions. The team suite mounts children through `MockAdapter`, whose `hang` already responds to abort, so it needed no double change.

## Alternatives considered

**Releasing test gates from `afterEach` bookkeeping instead of making the gate abortable.** A registry of unresolved gate resolvers would clean up the double's own contract from the outside and still hang if a future double forgot to register; cancellation is the model-call contract every real adapter already honors.

**Deleting roots when disposal fails, with the error logged.** That destroys the evidence a failed teardown leaves behind and can unlink a directory whose lock identity is still held; keeping the directory and rethrowing keeps both the diagnosis and the lock path stable.

**Observing release by reopening a recreated path.** Deleting the session directory and recreating it lets a fresh inode satisfy the probe while the original lock is still held; the probe must take over the original directory's write ownership instead, which is what the observer placement between disposal and deletion enforces.

**Disposing only the tool fiber, or waiting for children to leave the registry.** Neither closes the persistence service's open handles nor the parent/lead agent's write handle; only the owning root fiber's disposal reaches the full teardown chain (`FactoryOwnership.dispose` through `HandleTracker`'s close-every-handle effect).

## Consequences

The unchanged baseline of both suites passed 28/28 — an honest non-failure, since a small suite does not force GC collection — and the new regressions supplied the deterministic signal instead: with the Context disposal skipped (the old cleanup semantics), all seven resource tests fail on real observations before any removal, on `SessionAlreadyOwnedError` from the live kernel lock (probe veto inside `afterDispose`) or on a happens-before race (`cleanup-settled` before `disposer-reached`), while the 28 business tests keep passing. The fixed candidate passes 35/35 (17+1 control, 11+1 team, 5 regression), and two negative controls on the final bytes keep their discriminating power: skipping the disposal fails the seven resource tests; dropping only the `await` fails the deferred-disposer completion assertion and the held-gate probe veto. Both mutations restored byte-identically (SHA-256 re-verified, git blob `da23db7d7ba9351c0b6006b2e3a4b1c120f5cc6c` for the helper) and the suites returned to 35/35. Production AgentLoop destruction, the JSONL lease, persistence and Windows lock implementations, the public `MockAdapter`, and the shared read-handle helper are untouched. A caveat carried forward: cordis logs (not rethrows) disposer failures, so a handle-close failure inside `fiber.dispose()` surfaces through the logger and, when a probe observes the same fixture, as a veto; suites without observers can still delete a directory whose handle close failed loudly.
