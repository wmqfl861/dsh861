# Agent Note: Confirmed-delivery fence in the agent-team-teardown snapshot trigger

Status: implemented

English | [中文](2026-09-19-team-delivery-fence-r46.zh.md)

## Problem

The `agent-team-teardown` scenario trigger (`snapshots/sdk/agent-team-teardown/teardown-trigger.mjs`) armed the teammate close as soon as the held second model call, a pending teammate inbox, and an idle Lead all held. The pending-inbox fact is produced by the plugin's own `agentTeams.sendMessage` call, but the readiness check never waited for that send: the send's dispatch inserts into the teammate inbox synchronously, the `agent/inbox/inserted` handler re-entered evaluation while the send promise was still unsettled, and both the fulfill and reject callbacks only set a `pendingQueued` flag without inspecting the result. Two failure modes followed. The close could fire while the send was still in flight, and the CI consumers run (35376750928) lost exactly that race on Linux: the root Session persisted 41 of the expected 42 records, missing `team/message/delivered` for the scenario's second team message (`team/message/queued` was already durable), because `drainContinuableChildren` tore the teammate down before the Lead log recorded the delivery edge. And a send that settled `queued` or rejected still counted as success, so the scenario could report a green close over an undelivered message.

## Decision

The trigger now gates readiness on a verified settlement of that exact send. The send callbacks hand the result to a single `settleSendResult` step that requires `status: 'accepted'` plus a usable `messageId` string; `queued`, non-string or empty identities, unusable statuses, and rejections each record a distinct `sendStatus` (`queued` / `invalid` / `rejected`) with the exact reason in `state.json`'s new `sendMessageId` / `sendError` fields instead of any success flag. Readiness is the conjunction of the original scenario facts (held call, pending inbox, idle Lead) with `sendStatus === 'accepted'`, so both orderings — inbox inserted while the send is pending, or acceptance arriving before the remaining conditions — arm the close exactly once, and no path can arm it on a queued or rejected send. The auto and manual modes share this fact: the manual poll timer requires the same `state.ready`, so a trigger file that exists early cannot cross the acceptance barrier. Only the exact teammate's inbox inserts count toward the pending fact; an unrelated child's insert no longer arms anything. Production semantics are unchanged — `TeamMailbox.send` resolves `accepted` only after its dispatch checkpointed `team/message/delivered` in the Lead log, so the fence waits on durable delivery, not an in-memory flag, and the real close still goes through `subagents.drainContinuableChildren(lead, [teammateId])` with the held call's abort handshake, timer unload, and effect cleanup intact.

A deterministic regression, `scripts/tests/agent-team-teardown-trigger.spec.ts`, drives the actual repository module through a test-owned subprocess fixture (`scripts/tests/fixtures/agent-team-teardown-trigger-driver.mjs`) whose fake Context controls send and drain settlement order explicitly; the spec re-derives the module's SHA-256 to prove it exercised the repository file, not a copy. Seven scenarios pin the causal orders: inbox-before-acceptance, acceptance-before-conditions, queued, reject, invalid identity, manual mode with a pre-existing trigger file plus an unrelated child and duplicate events, and the abort handshake with a real close error. On the unmodified module the spec fails 7 of 10 tests with the required first failure — `no-close-while-send-pending` observes the drain firing while the send is pending. Two independent negative controls mutate only the trigger: removing the acceptance precondition fails at exactly that pending-send assertion, and treating queued or reject as confirmation fails the queued and reject no-close branches; both mutants are restored byte-identically (SHA-256 re-verified) with the spec returning to 10/10. The manual teardown adapter (`snapshots/sdk/teardown.snapshot.ts`) now also pins the fence against the real runtime: the armed gate requires `sendStatus === 'accepted'` with the message identity, the pre-close Lead log must contain `team/message/queued` and `team/message/delivered` for that exact `messageId` with the teammate as target and delivery after the queue edge, delivery must precede every close-produced root event, the child's pending inbox splice behind the held step must carry the same message identity, and a send that settles without acceptance fails the armed poll immediately with the recorded `sendError` rather than timing out.

## Alternatives considered

**Waiting on the inbox insert alone.** The insert happens during the send's dispatch, before settlement; treating it as acknowledgement is precisely the race that lost `team/message/delivered` in CI.

**Treating send fulfillment as success regardless of status.** `TeamMailbox.send` resolves `queued` when delivery could not complete; a green close over an undelivered message is the false-success mode this fence exists to remove.

**Reading the Lead log from the trigger to confirm delivery.** The trigger would re-implement journal observation that the mailbox already performs; the `accepted` settlement is the mailbox's own statement that the delivery edge is durable.

**Refreshing the golden to drop the delivered event.** The golden's 42-record root session is the recorded contract; the defect was the trigger's ordering, not the expectation.

## Consequences

The real-SDK adapter passes 2/2 on this Windows host with the same message identity verified queued and delivered before the close suffix (`team-message-… delivered@32`, close suffix starting at seq 33), so the scenario's persisted output now deterministically matches the committed golden shape that CI previously lost to the race. No production package, shared `sdk.snapshot.ts`, normalizer, golden, replay input, lockfile, or workflow changed. The shared automatic lane still cannot complete on this Windows host: its fixture hydration embeds a raw backslash `{{cwd}}` into JSONL text, so `llm-replay` fails to load and the first prompt reports `cannot create effect on inactive context` — the pre-existing r44 gap reproduced identically before any golden comparison, and the Linux CI lane remains the authority for the full comparison. The subagent-teardown pwsh/bash tool-schema platform difference and the other preserved r44/r45 environment findings are untouched.
