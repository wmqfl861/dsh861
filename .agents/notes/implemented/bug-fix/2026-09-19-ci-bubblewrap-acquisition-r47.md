# Agent Note: Pinned-time Ubuntu snapshot acquisition restores the CI bubblewrap payload

Status: implemented

English | [中文](2026-09-19-ci-bubblewrap-acquisition-r47.zh.md)

## Problem

`scripts/prepare-ci-bubblewrap.sh` downloads the pinned `bubblewrap_0.9.0-1ubuntu0.1_amd64.deb` (SHA-256 `1b506492…`) from the rolling `archive.ubuntu.com` pool. That pool dropped the file, so CI run 35413575204's two Linux lanes (jobs 105817753016 and 105817753073) each failed the preparation step at curl's fourth HTTP 404 with step exit 22, before any test started. Restoring CI needs a reproducible acquisition of the same bytes; substituting a newer bubblewrap would change the pinned payload identity and silently drift the sandbox baseline.

## Decision

The script now downloads the identical pinned payload from Ubuntu's official snapshot service at a fixed UTC timestamp (`https://snapshot.ubuntu.com/ubuntu/20260901T000000Z/pool/main/b/bubblewrap/bubblewrap_0.9.0-1ubuntu0.1_amd64.deb`), with a three-line source note recording why the rolling pool URL is gone and that payload identity stays bound by the SHA-256, not by the source host. Nothing else in the script changed: same version, same SHA-256, same curl failure flags, checksum still precedes extraction, same platform and environment gates, same tolerated-sysctl behavior, same functional probe and failure exits. The bytes were verified real before the edit: the snapshot returned HTTP 200 with zero redirects and 50178 bytes, and the digest matched the pinned SHA-256 under both Git Bash `sha256sum` and PowerShell `Get-FileHash`; a read-only listing of the deb's control member confirmed `Package: bubblewrap`, `Version: 0.9.0-1ubuntu0.1`, `Architecture: amd64`.

A direct regression, `scripts/prepare-ci-bubblewrap.spec.ts`, executes the real repository script under real Bash with every external effect (`uname`, `curl`, `sha256sum`, `dpkg-deb`, `sudo`, and the extracted `bwrap`) replaced by test-owned PATH stubs that only record argv and return scenario-controlled exit codes; the controlled stub network serves exactly the verified snapshot URL and refuses the dead rolling source like any other unverified source. Thirteen tests pin: end-to-end success from the verified source (call order, single success line, `GITHUB_PATH` publication, digest checked against the pinned identity), the tolerated absent sysctl knob, 404 and connection-failure download stops (exit 22/7 with no later phase), digest-mismatch rejection before any extraction, extraction failure before privilege or probe, fatal probe failure without a success line (the pre-probe `GITHUB_PATH` write is asserted as publication, not probe success), non-Linux and non-x86_64 refusal before any download, and missing `RUNNER_TEMP`/`GITHUB_PATH` failing loud. Everything runs offline with writes confined to per-run random temporary directories removed in `afterAll`; the suite self-skips where no POSIX/Git Bash exists, matching the repo's bash-requiring suite convention. On the unmodified script the spec fails 6 of 13 exactly at the dead source. Two negative controls proved discovery: restoring only the dead URL failed the same six, and appending only ` || true` to the digest check failed exactly the digest-mismatch test because the script crossed into extraction; both mutants were syntax-valid (`bash -n` 0), restored byte-identically (cmp, git blob, and SHA-256 re-verified), and the spec returned to 13/13 after each restore.

## Consequences

Linux CI lanes can again fetch the pinned payload byte-identically, which unblocks the preparation step; it does not promise the runs go green (the schema, snapshot, and coverage findings remain owned by the new runs). Canonical's UBUNTU-CVE-2026-87766 still lists 0.9.0-1ubuntu0.1 as affected: this is an acquisition restoration, NOT a CVE closure or security upgrade, the upgrade stage and P0-B stay blocked, and the pin must not be read as approval for new deployments running real untrusted workloads. The repository's supply-chain policy does not yet cover CVE-listed CI payloads ([policy-conclusion.md](../../../../development/remediation/2026-09-19/ci-bubblewrap-acquisition-r47/windows-execution/policy-conclusion.md) records the not-covered finding), so the same-byte pin continues under an explicitly recorded risk until a future round pins a verified fixed Noble build with its own SHA-256, runner dependency compatibility (`libc6`/`libcap2`/`libselinux1`), and a re-run functional probe. The real Linux unpack, sysctl behavior, and bwrap functional probe remain executed only by the original CI on its ephemeral runners; the local stubs prove control flow, not platform behavior. Evidence: [windows-execution/FINDINGS.md](../../../../development/remediation/2026-09-19/ci-bubblewrap-acquisition-r47/windows-execution/FINDINGS.md).

## Alternatives considered

**Automatic fallback across mirrors.** Rejected: unverified mirrors and latest links replace the pinned identity with whatever they happen to serve; the failure stays loud until the official pinned-time source is the one being verified.

**Upgrading to a fixed bubblewrap version in this round.** Rejected: a version change is a payload-identity change needing its own verified official source, SHA-256, runner dependency compatibility, and sandbox behavior validation (USN-8779-x sequencing); it is the separate migration proposal, not a URL repair.

**Trusting the filename as package identity.** Rejected: the deb's control fields were checked read-only, but the identity binding remains the pinned SHA-256 verified against the actually downloaded bytes.
