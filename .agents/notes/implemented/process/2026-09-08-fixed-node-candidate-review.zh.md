# Agent Note: 项目节点的固定候选与真实 CLI 审核

Status: implemented

[English](2026-09-08-fixed-node-candidate-review.md) | 中文

## 问题

并行任务可能在审核者检查文件时继续改动文件。已跟踪文件的差异会遗漏新增未跟踪文档，仅凭角色标签或工具成功退出，也无法确定谁审核了哪些内容。

构建与无密钥启动证据所能证明的范围小于产品验收。把计划中的命令、跳过的检查或 mock 响应视为已完成的产品能力，会抹去这一区别。

## 决定

已采用的[节点开发规则](../../../../NODE_DEVELOPMENT_RULES.md)将详细计划及其修订交给真实 Codex CLI（命令行界面），使用 `gpt-6-astra` 和思考等级 `max`；将实施与修复交给 ZCode；将强制独立审核交给真实 OpenCode CLI，使用 `zhipuai-coding-plan/glm-5.3` 和 variant `max`。ZCode 可以将实施工作委派给内置 subagent；这些助手不计作指定的计划者或审核者。上述分工适用于项目开发，不构成产品岗位的永久绑定。

每次声称执行的外部调用都须有程序路径、版本与哈希、模型与思考等级参数、起止时间、退出结果、提示词哈希及原始输出引用。传入参数与可观测运行事实分别记录；模型自述身份不能证明其中任何一项。指定模型不可用、思考等级不受支持、身份无法核实或输出缺失时，节点阻塞，不以替代调用继续推进。计划原文及修订保留各自的调用证据；实施者不得悄悄改写验收标准。

整合者固定基线 HEAD，并建立候选文件清单，覆盖已暂存、未暂存及未跟踪工作中的新增、修改与删除文件。每项记录规范化的仓库相对路径、类型、字节数及 SHA-256；工具链、验证与构建证据通过带哈希的引用关联。清单自身的哈希单独保存。后续状态与审核回执标识候选，但不纳入候选自身的哈希输入，也不改变候选内容。

实施任务全部结束且候选内容冻结后才开始审核。审核者读取实际文件，不修改文件。任何候选内容变化都须产生新一轮，并保留此前回执。只有 OpenCode 对当前候选明确给出 `PASS`，且每项必需检查实际成功，才可规划下一节点。`FAIL` 要求修复后再次审核；`BLOCKED` 保留缺少的条件。

验证区分源码或配置核查、实际执行的命令、需要适配与验证的可复用组件、需要实现的需求以及缺少的前提条件。记录保留 `NOT_RUN`、`OUT_OF_SCOPE`、跳过、重试、超时与原始失败。没有绑定候选的审核结论时，CLI 退出零不能证明节点完成；未执行的必需检查或被跳过的必选测试同样不能证明节点完成。

[P0-A 计划](../../../../development/nodes/P0-A/plan.v1.md)负责操作步骤，并将验收范围限定为 Windows 构建与启动基线。无密钥或使用 mock 的检查仅证明实际验证过的性质。开发期间的 CLI 调用不能证明产品 harness 隔离，基线成功也不代表 P0 完成，或权限、记忆、工作流及真实模型集成的产品验收条件完成。

## 考虑过的替代方案

**用内置角色标签充当独立计划或审核。** 节点规则不采纳此方式，因为标签无法证明指定外部产品使用获准设置实际运行。真实子进程调用需要调用记录，也依赖工具与认证条件可用。

**只审核已跟踪文件的 Git 差异。** 规则不采纳此方式，因为新增未跟踪的需求、计划、Note 和证据可能影响验收，却不会出现在该差异中。明确文件覆盖范围并记录内容哈希会增加记录工作，但能够标识完整候选。

**审核期间继续编辑，或修改后复用此前结论。** 规则不采纳此方式，因为结论描述的内容与实际内容不再一致。逐轮冻结候选并保留独立记录，意味着审核须等到整合结束，修复后还须再次审核。

**把退出零、跳过检查或基线成功视为充分验收。** 规则与计划不采纳此方式，因为它们各自证明的范围小于节点或产品声明。必需执行证据与明确绑定候选的审核结论保留这些限制，代价是证据缺失时阻塞进展。

## 影响

审核者可以确定结论对应的实现与证据，包括未跟踪的任务产物。此流程增加哈希计算、可归属日志和候选变化后的再次审核；外部 CLI 或认证失败可能阻塞开发。整合者与审核者负责落实这些义务，该流程本身不交付产品授权、隔离或审计能力。

本 Agent Note 的 `implemented` 状态记录流程决定已采用。节点完成以绑定候选的审核回执和验证证据为依据；本 Note 不声称任何节点或检查已通过。
